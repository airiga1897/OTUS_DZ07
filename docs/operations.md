# Эксплуатация

Основная последовательность: реквизиты → deploy → verify → open → отдельный
destroy. Команды из [README](../README.md) выполняются в PowerShell из корня клона.

## Вход в Kibana

`open` показывает адрес Kibana. Логин — `elastic`, пароль — значение поля
`elastic` в локальном `.local/secrets.json`. Поле `kibana` используется службой
`kibana_system`, а не для входа через браузер. Команда копирования пароля без
вывода в консоль приведена в [README](../README.md).

Для просмотра событий откройте **Analytics → Discover** и выберите
`logs-otus-*`; проверьте диапазон времени. Сохранённый дешборд — отдельный
объект Kibana: доступность службы сама по себе не подтверждает его корректность.
Локальная проверка создания и `verify` учитывают собственные поисковые
метаданные дешборда `kibanaSavedObjectMeta.searchSourceJSON`.
Это не заменяет проверку отображения в браузере. Изменение локального кода
не исправляет автоматически объект уже созданного стенда; его обновление
требует отдельного применения. Правка включена в исходники `v1.1.1` и проверена
локально; новое развёртывание с ней в облаке ещё не испытывалось.

Чтобы просмотреть события одной ВМ, в строке KQL задайте, например,
`host.name: "otus-dz07-es1"`. Точное имя выбирается из значений поля
`host.name`; при другом пространстве имён используйте фактические значения.
Для фильтра по службе: `host.name: "otus-dz07-app" and service.name: "nginx"`.
Добавьте в таблицу поля `host.name`, `service.name`, `message` и выберите
диапазон **Last 15 minutes** или **Last 1 hour**, затем **Refresh**.

## Ход выполнения команд

До загрузки зависимостей SSH и облачного API контроллер сообщает о начале
подготовки. После загрузки зависимостей и локальной конфигурации выводится
длительность этого этапа. Используются настройки `config/logging.json` и
`--log-level`; при уровне WARNING информационные сообщения скрыты. Запуск
самого Python и загрузка начального модуля логирования предшествуют этому
сообщению. Отсутствие вывода на этом участке требует отдельной диагностики
локального окружения. Порядок сообщений проверен локально; длительность
следующего ручного запуска заранее не гарантируется.

Предварительные проверки входят в deploy; отдельный `preflight` необязателен
и не создаёт облачные ресурсы. Обычные verify и test-cycle не добавляют es4
и не выключают узлы. Расширение ES и проверка отказоустойчивости запускаются
только явными дополнительными командами из README.

Основу задания составляют три ES-узла и app с источниками логов и Kibana.
Причины дополнительных механизмов, их цена сопровождения и границы повторного
использования описаны в [ADR-0007](adr/0007-scope-and-reuse.md). Облачный отчёт
подтверждает указанную в нём версию; локальные mock-проверки не подтверждают
работоспособность новых изменений в облаке.

## Аудит при удалении

При `destroy` без локального стенда адаптер Selectel проверяет обнаруженные
пулы и общие ресурсы. В ru-4 и ru-5 отсутствие `volumev3` допускается явной
политикой `audit.service_exclusions` в `config/cloud.json`: диски исключены
из этой проверки, что отражается в журнале и отчёте. Это не подтверждение их
отсутствия. ВМ и сети проверяются; опубликованный дисковый API также проверяется.
Для сохранённого стенда и поиска при повреждении контекста исключения не
действуют. Подробности — в [ADR-0006](adr/0006-destroy-audit-scope.md).

## Повторное развёртывание

deploy использует сохранённые размещение, state и ID ресурсов. Перед apply
проверяется сохранённый Terraform-план. Удаление, замена и изменение существующих
ресурсов блокируются. Уменьшение и перенос — отдельные сценарии.
Ошибка настройки сохраняет ресурсы и контекст для диагностики.

При чтении состояния OpenStack может дополнить вычисляемые поля после создания
ВМ и привязки порта. Узкий допуск в `selectel_refresh.py` сверяет ID, владельца,
сохранённые сеть, подсеть, адрес и связь floating IP. Для метаданных разрешено
только наблюдённое поле `x_cloud_maintenance` при сохранении маркера владельца.
DNS и ранее неизвестная QoS-политика принимаются только при первоначальной
привязке порта к собственной ВМ; смена действующей политики блокируется.
Это допуск обновления наблюдаемого состояния: запланированные изменения,
замены и удаления существующих ресурсов по-прежнему запрещены.

Для `scheduler_hints` допускается только эквивалентное представление пустых
необязательных полей (`null`, пустая коллекция или строка нужного типа) при
неизменной сохранённой группе и включённом разнесении ES. Смена группы,
непустые дополнительные ограничения и неизвестные поля блокируются.
Формы разрешённой нормализации проверяются локальными тестами;
облачный цикл подтверждает повторное применение конкретного стенда,
а не допустимость произвольного изменения этого блока.

До очистки ошибка любой команды Terraform сохраняется отдельным обезличенным
JSON в `docs/terraform-faults/`: этап, операция, размещение, ID тестового запуска,
код завершения и полный текст ошибки без реквизитов доступа. Имя уникально;
очистка сохраняет этот файл, а `failure_evidence` в отчёте test-cycle указывает
на него. Локальные журналы команд дополняются, а не перезаписываются при destroy.
В `docs/placement-faults/` сохраняются доступные `fault` собственных ВМ,
состояние ресурсов Глобального роутера и дополнительные поля ошибки, если
их возвращает API. Перед запросом проверяется принадлежность ресурса.
Ошибки чтения или сохранения диагностики отмечаются отдельно, сохраняют
исходную ошибку и не отменяют очистку временного стенда. Ответ API со
статусом `ERROR` без пояснения не трактуется как установленная внутренняя причина.
[Правила подбора, маски дисков и размещение ru-3b](placement.md).

Ansible настраивает службы; обработчики перезапускают их при изменениях.
Его выполнение на app отделено от SSH-сессии локального контроллера.
При обрыве сети сохраняются ID операции и данные восстановления, повторный
`deploy` продолжает наблюдение. Неизвестный из-за связи результат не считается
ошибкой Ansible и не разрешает новый параллельный запуск.
[Состояния операции, ограничения времени и журналы](ansible-operations.md).
Elasticsearch при повторной настройке обрабатывается последовательно с проверкой
кворума. PostgreSQL работает в одном экземпляре на app. Кластер PostgreSQL,
добавление его реплик и проверка переключения ведущего узла не поддерживаются.
Миграции приложения повторяемы; постоянный маркер
защищает БД от повторной загрузки фикстуры. Исходники не заменяют media.

### Ручная проверка восстановления правил доступа

Выполняйте сценарий на собственном тестовом стенде из корня клона, которым
его развернули. Нужны рабочий SSH, два сохранённых IPv4 `/32` и право
удалять правила группы безопасности в Selectel. В PowerShell загрузите
реквизиты командой `. .\scripts\env.ps1`, если сессия новая. Обычный
`verify` перед испытанием должен завершиться успешно.

```powershell
.\.tools\venv\Scripts\python.exe scripts/lab.py verify
if ($LASTEXITCODE -ne 0) { throw 'Сначала устраните ошибку исходной проверки' }
```

**1. Сохраните ID ресурсов и определите одно правило для испытания.**
Используйте второй подтверждённый IPv4, который сейчас не нужен для доступа
к Kibana. Снимки хранятся в памяти этой сессии PowerShell.

```powershell
function Get-StandResourceIds {
    $journal = Get-Content .\.local\staged-deployment.json -Raw -ErrorAction Stop |
        ConvertFrom-Json -ErrorAction Stop
    $ids = @{}
    foreach ($stage in $journal.stages.PSObject.Properties) {
        if ($stage.Value.status -ne 'active') { continue }
        if (-not $stage.Value.identities) {
            throw "В журнале нет ID активного этапа $($stage.Name)"
        }
        foreach ($resource in $stage.Value.identities.PSObject.Properties) {
            $ids["$($stage.Name)|$($resource.Name)"] = $resource.Value
        }
    }
    if ($ids.Count -eq 0) { throw 'В журнале нет ID активного стенда' }
    return $ids
}

$cidr = '<ВТОРОЙ_IPV4>/32'
$journal = Get-Content .\.local\staged-deployment.json -Raw | ConvertFrom-Json
$pool = $journal.stages.app.candidate.region
$network = "network-$pool"
$stage = $journal.stages.PSObject.Properties[$network].Value
if ($stage.status -ne 'active' -or $cidr -notin @($stage.inputs.admin_cidrs)) {
    throw 'Проверьте, что указанный /32 сохранён в активной сети app'
}
$address = 'module.stage.openstack_networking_secgroup_rule_v2.kibana["{0}"]' -f $cidr
$key = "$network|$address"
$before = Get-StandResourceIds
if (-not $before[$key]) { throw 'В журнале нет ID выбранного правила' }

[pscustomobject]@{
    Pool = $pool
    SecurityGroupId = $stage.output.security_group_id
    RuleId = $before[$key]
    Source = $cidr
    Port = $stage.inputs.kibana_port
}
```

**2. Удалите ровно одно входящее правило TCP для Kibana.** В панели Selectel
откройте группу безопасности ВМ `app` в выведенном пуле. Сверьте ID группы,
источник `/32` и порт Kibana, по умолчанию 5601. Если интерфейс показывает ID
правила, сверяйте и его. Удалите только совпавшую запись. При неоднозначности
остановитесь. Оставьте оба правила TCP/22, правило Kibana для первого адреса
и привязку группы к ВМ.

Сразу запустите `verify`. Ожидается ошибка с пулом `app`, портом Kibana и
выбранным `/32`. Если проверка сообщает другую ошибку, восстановите удалённое
правило командой ниже и разберите причину отдельно.

```powershell
.\.tools\venv\Scripts\python.exe scripts/lab.py verify
```

**3. Восстановите правило и проверьте стенд.** Для проверки отдельной команды
выполните `repair-access`. Чтобы испытать восстановление при повторном
развёртывании, используйте `deploy --repair-access` вместо неё.

```powershell
.\.tools\venv\Scripts\python.exe scripts/lab.py repair-access
# Альтернативный запуск для отдельного прогона
# .\.tools\venv\Scripts\python.exe scripts/lab.py deploy --repair-access
```

После успеха в пуле `app` должно быть создано одно правило. Сверьте в Selectel
входящее правило с тем же портом и источником. Если панель показывает ID,
сравните его с `$after[$key]` после выполнения блока ниже. Повторите обычный
`verify`, чтобы подтвердить правила обоих адресов через API и работу стенда
по SSH.

```powershell
.\.tools\venv\Scripts\python.exe scripts/lab.py verify
if ($LASTEXITCODE -ne 0) { throw 'Проверка после восстановления завершилась с ошибкой' }
$after = Get-StandResourceIds
if (-not $after[$key] -or $after[$key] -ceq $before[$key]) {
    throw 'ID восстановленного правила отсутствует или не изменился'
}
$otherChanges = @(@($before.Keys) + @($after.Keys) | Sort-Object -Unique |
    Where-Object { $_ -ne $key -and $before[$_] -cne $after[$_] })
if ($otherChanges.Count -gt 0) {
    throw "Изменились другие ресурсы: $($otherChanges -join ', ')"
}
'Изменился только ID восстановленного правила Kibana.'
```

Для проверки второго режима повторите сценарий с новым исходным снимком.
Если восстановление остановилось, сохраните журнал и state для диагностики.
Повторный запуск той же команды может завершить сохранённую операцию. Если
правило уже есть в Selectel, а его ID отсутствует в Terraform state, требуется
отдельная сверка. Сценарий и сравнение ID проверяются локально на имитациях;
облачное выполнение подтверждается ручным прогоном.

## Проверки и очистка

Команды `deploy`, `verify`, `open` и `destroy` приведены в разделе
[«Развёртывание из чистого клона»](releases.md#развёртывание-из-чистого-клона).
Полный локальный набор предназначен для разработки и отладки.
[Инструменты, область измерения и локальные журналы](local-quality.md).

Параметры чтения Selectel API задаются в `config/cloud.json`: ограниченное
число повторов для временных ошибок GET. Запросы изменения ресурсов и
авторизации автоматически не повторяются. Ошибки проверки сертификата и
постоянные HTTP-ошибки завершаются сразу; проверка TLS сохраняется.

Проверка Terraform-плана отличает планируемые изменения от обновления
вычисляемых сведений. Для загрузочного диска допускается обнаружение его
подключения только к сохранённой ВМ того же этапа, с прежним ID диска.
Отключение диска, подключение к чужой ВМ, изменение размера, типа, зоны,
удаление или замена ресурса блокируются. При отклонении плана сохраняются
адреса ресурсов, действия и имена изменившихся полей. Для `scheduler_hints`
дополнительно сохраняются типы и пустота известных полей, число неизвестных
полей и результат сравнения группы с сохранённой. Значения, идентификаторы
групп, содержимое дополнительных параметров и сырой план не публикуются.
Диагностика записывается до очистки и сохраняется после неё; ошибка записи
не заменяет исходную причину отказа и не разрешает применение плана.

verify создаёт контрольную запись и media через приложение, проверяет SQL,
не выключая ВМ. Для Elasticsearch проверяются штатный состав кластера,
зелёное состояние, чтение и запись документов. Проверяются источники журналов и объекты Kibana
через API; это не заменяет визуальную проверку дашборда.

test-cycle работает только с пустого состояния. Он проверяет повторный deploy,
сохранность ID ВМ/дисков/портов, UUID кластера и ID ES-узлов, документы,
данные приложения и media. В finally очищаются только ресурсы своего запуска
с аудитом state и API. При ошибке удаления данные восстановления сохраняются.

При ошибке удаления узла остальные узлы очищаются независимо. Для каждого
пула подключение ожидает удаления своих узлов, сеть — своих узлов и подключения.
Глобальный роутер ожидает удаления всех подключений. Статус `deleted` выставляется
только после проверки state и API. Зависимые этапы блокируются до повторного
destroy; сети и подключения независимого пула продолжают удаляться. Если пул
узла неизвестен, сохраняются все потенциальные родительские этапы.

Перед удалением любых ВМ контроллер подтверждает остановку сохранённой
systemd-операции Ansible и её дочерних процессов. При недоступности управления
удаление блокируется, а файлы восстановления остаются для повторного `destroy`.
Ошибки завершающих действий не заменяют первоначальную ошибку настройки.

После успешного destroy удаляются ненужные служебные файлы; реквизиты разработки
сохраняются до явного решения пользователя. --purge-artifacts очищает также
подтверждённый префикс ДЗ07 в S3, сохраняя бакет.

В test-cycle остаются три ES-узла, новые узлы не добавляются. Mock-тесты
не заменяют облачный прогон. [Полный test-cycle опубликованного выпуска](release-cloud-acceptance.json)
подтвердил сайт, все источники логов, Kibana, повторный deploy,
сохранность документов и ID и очистку через state и API.

### Проверка Kibana и сохранение результатов

После `deploy` выполните `verify` и `open`. Откройте Kibana по адресу из
вывода `open` и войдите с реквизитами из раздела [«Вход в Kibana»](#вход-в-kibana).

- [ ] В **Analytics → Dashboards** откройте **OTUS DZ07 — журналы серверов**
  (`otus-logs`). Выберите диапазон, охватывающий развёртывание, и нажмите
  **Refresh**. Убедитесь, что таблица загрузилась и содержит события со
  столбцами `host.name`, `service.name` и `message`.
- [ ] В **Analytics → Discover** выберите представление `logs-otus-*`.
  Добавьте столбцы `host.name`, `service.name` и `message`. Проверьте все
  четыре ВМ по очереди. Например, для первого узла Elasticsearch введите
  в строке KQL `host.name: "otus-dz07-es1"`. Имена остальных ВМ возьмите
  из значений поля `host.name`.

  | ВМ | Ожидаемые значения `service.name` |
  | --- | --- |
  | `app` | `nginx`, `haproxy`, `postgresql`, `django`, `kibana`, `system` |
  | `es1`, `es2`, `es3` | `elasticsearch` и `system` на каждой ВМ |

  Сверьте все 12 сочетаний ВМ и источника. Для проверки свежих событий
  обновите страницу портала, затем найдите запись с новым `@timestamp`
  по фильтру `host.name: "otus-dz07-app" and service.name: "nginx"`.
- [ ] До `destroy` сохраните скриншот открытого дешборда с названием,
  диапазоном времени и строками событий. Сохраните также скриншот Discover
  с разбивкой по `host.name`, на котором видны все четыре ВМ. Можно приложить
  отдельный скриншот для каждой ВМ с её фильтром.
- [ ] Сохраните отчёты текущего запуска `verify`.

  | Отчёт | Ожидаемый результат |
  | --- | --- |
  | [Журналы и Kibana](logs-verification.json) | Три узла Elasticsearch, состояние `green`, события по всем ожидаемым источникам и доступные объекты Kibana |
  | [Сайт и БД](verification.json) | Сайт отвечает, проверки чтения и записи данных пройдены |

- [ ] Выполните `destroy` из того же клона. Сохраните свежий
  [отчёт об очистке](cleanup-result.json) с `success: true`, `audit_complete: true`
  и `managed_remaining: 0`.

Для подтверждения результатов используйте обезличенные скриншоты и отчёты одного прогона.
Перед передачей материалов скройте публичные IP-адреса, реквизиты и чувствительное
содержимое событий.

## Последовательное размещение

`destroy` использует пулы сохранённых этапов и незавершённых попыток, а общие
ресурсы Глобального роутера проверяет отдельно, если журнал содержит попытки
их создания. При утрате контекста расширенный поиск включает и общие ресурсы.
Предпочтения нового размещения
не меняют область удаления. При недостатке данных журнал сообщает причину
расширенного поиска по пространству имён проекта; это не разрешение удалять
объекты по одному совпадению имени. Ошибка любого чтения блокирует подтверждение
очистки и удаление служебных файлов. Независимые чтения ограничены
`audit.read_workers` в [config/cloud.json](../config/cloud.json).
Подробности — [ADR-0006](adr/0006-destroy-audit-scope.md).

Для нового стенда используется [последовательный подбор](distributed-placement.md)
с отдельными state в `.local/stages/`. Обычный deploy продолжает незавершённый
этап и сохраняет успешные ресурсы. Контекст `.local/staged-deployment.json`
нельзя удалять до подтверждённой очистки всех использованных пулов и общих этапов.
Изменение порядка пулов не переносит действующие узлы. Подключения между
пулами создаются через Глобальный роутер после подтверждения ВМ во втором пуле,
без публичных IP на ES-узлах. Настройки запуска читаются из `.env`:
[приоритет и ограничения изменения](run-settings.md). Созданная текущей
неуспешной попыткой сеть очищается только при отсутствии использующих её ВМ
и после аудита state/API; занятые и сохранённые сети не удаляются этим шагом.

При ошибке destroy повторяется та же команда с сохранёнными служебными файлами.
Если контекст утрачен или state изменён вне контроллера, автоматическая работа
блокируется до явного восстановления привязки. Прежний state одного пула
не преобразуется автоматически в последовательный: его удаление и новый
стенд являются отдельными операциями.
