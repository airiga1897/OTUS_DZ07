# Эксплуатация

Основная последовательность: реквизиты → deploy → verify → open → отдельный
destroy. Команды из [README](../README.md) выполняются в PowerShell из корня клона.

## Повторное развёртывание

deploy использует сохранённые размещение, state и ID ресурсов. Перед apply
проверяется сохранённый Terraform-план. Удаление, замена и изменение существующих
ресурсов блокируются. Уменьшение и перенос — отдельные сценарии.
Ошибка настройки сохраняет ресурсы и контекст для диагностики.

При чтении состояния OpenStack может дополнить вычисляемые поля после создания
ВМ и привязки порта. Узкий допуск в `selectel_refresh.py` сверяет ID, владельца,
сохранённые сеть, подсеть, адрес и связь floating IP. Для метаданных разрешено
только наблюдённое поле `x_cloud_maintenance` при сохранении маркера владельца.
DNS и ранее неизвестная QoS-политика принимаются только при первоначальной
привязке порта к собственной ВМ; смена действующей политики блокируется.
Это допуск обновления наблюдаемого состояния: запланированные изменения,
замены и удаления существующих ресурсов по-прежнему запрещены.

Для `scheduler_hints` допускается только эквивалентное представление пустых
необязательных полей (`null`, пустая коллекция или строка нужного типа) при
неизменной сохранённой группе и включённом разнесении ES. Смена группы,
непустые дополнительные ограничения и неизвестные поля блокируются.
Предыдущий облачный отчёт не содержит значений этого блока, поэтому точная
форма прежнего изменения не установлена; разрешённая нормализация проверена локально.

До очистки ошибка любой команды Terraform сохраняется отдельным обезличенным
JSON в `docs/terraform-faults/`: этап, операция, размещение, ID тестового запуска,
код завершения и полный текст ошибки без реквизитов доступа. Имя уникально;
очистка сохраняет этот файл, а `failure_evidence` в отчёте test-cycle указывает
на него. Локальные журналы команд дополняются, а не перезаписываются при destroy.
В `docs/placement-faults/` сохраняются доступные `fault` собственных ВМ,
состояние ресурсов Глобального роутера и дополнительные поля ошибки, если
их возвращает API. Перед запросом проверяется принадлежность ресурса.
Ошибки чтения или сохранения диагностики отмечаются отдельно, сохраняют
исходную ошибку и не отменяют очистку временного стенда. Ответ API со
статусом `ERROR` без пояснения не трактуется как установленная внутренняя причина.
[Правила подбора, маски дисков и размещение ru-3b](placement.md).

Ansible настраивает службы; обработчики перезапускают их при изменениях.
Его выполнение на app отделено от SSH-сессии локального контроллера.
При обрыве сети сохраняются ID операции и данные восстановления, повторный
`deploy` продолжает наблюдение. Неизвестный из-за связи результат не считается
ошибкой Ansible и не разрешает новый параллельный запуск.
[Состояния операции, ограничения времени и журналы](ansible-operations.md).
Elasticsearch при повторной настройке обрабатывается последовательно с проверкой
кворума. PostgreSQL работает локально без Patroni и etcd. Миграции приложения повторяемы; постоянный маркер
защищает БД от повторной загрузки фикстуры. Исходники не заменяют media.

## Проверки и очистка

Локальные проверки выполняются из корня клона после `scripts/setup.ps1`:

```powershell
.\.tools\venv\Scripts\python.exe scripts/check.py
```

Команда запускает тесты контроллера, доставки файлов, настройки служб и Django,
блокирует внешние соединения и сохраняет покрытие строк и ветвей в
`.tools/coverage/`. Подставные API не подтверждают работу облака.
Из измерения исключены тесты, миграции Django и сам измеряющий скрипт;
непокрытые ветви рабочего кода остаются в отчёте.

Локальная проверка: 750 тестов Python/Django прошли,
покрытие строк — 100%, ветвей — 98,2143%. Пороги 95% и 90% достигнуты
без дополнительных исключений. До полного покрытия ветвей остаются 42 перехода;
[список непокрытых участков](coverage-remaining.json). [Результаты и область проверки](coverage-target-verification.json).
Измерение включает также неимпортированные сценарии в каталогах без `__init__.py`.

Параметры чтения Selectel API задаются в `config/cloud.json`: ограниченное
число повторов для временных ошибок GET. Запросы изменения ресурсов и
авторизации автоматически не повторяются. Ошибки проверки сертификата и
постоянные HTTP-ошибки завершаются сразу; проверка TLS сохраняется.

Проверка Terraform-плана отличает планируемые изменения от обновления
вычисляемых сведений. Для загрузочного диска допускается обнаружение его
подключения только к сохранённой ВМ того же этапа, с прежним ID диска.
Отключение диска, подключение к чужой ВМ, изменение размера, типа, зоны,
удаление или замена ресурса блокируются. При отклонении плана сохраняются
адреса ресурсов, действия и имена изменившихся полей. Для `scheduler_hints`
дополнительно сохраняются типы и пустота известных полей, число неизвестных
полей и результат сравнения группы с сохранённой. Значения, идентификаторы
групп, содержимое дополнительных параметров и сырой план не публикуются.
Диагностика записывается до очистки и сохраняется после неё; ошибка записи
не заменяет исходную причину отказа и не разрешает применение плана.

verify создаёт контрольную запись и media через приложение, проверяет SQL,
не выключая ВМ. Для Elasticsearch проверяются штатный состав кластера,
зелёное состояние, чтение и запись документов. Проверяются источники журналов и объекты Kibana
через API; это не заменяет визуальную проверку дашборда.

test-cycle работает только с пустого состояния. Он проверяет повторный deploy,
сохранность ID ВМ/дисков/портов, UUID кластера и ID ES-узлов, документы,
данные приложения и media. В finally очищаются только ресурсы своего запуска
с аудитом state и API. При ошибке удаления данные восстановления сохраняются.

При ошибке удаления узла остальные узлы очищаются независимо. Для каждого
пула подключение ожидает удаления своих узлов, сеть — своих узлов и подключения.
Глобальный роутер ожидает удаления всех подключений. Статус `deleted` выставляется
только после проверки state и API. Зависимые этапы блокируются до повторного
destroy; сети и подключения независимого пула продолжают удаляться. Если пул
узла неизвестен, сохраняются все потенциальные родительские этапы.

Перед удалением любых ВМ контроллер подтверждает остановку сохранённой
systemd-операции Ansible и её дочерних процессов. При недоступности управления
удаление блокируется, а файлы восстановления остаются для повторного `destroy`.
Ошибки завершающих действий не заменяют первоначальную ошибку настройки.

После успешного destroy удаляются ненужные служебные файлы; реквизиты разработки
сохраняются до явного решения пользователя. --purge-artifacts очищает также
подтверждённый префикс ДЗ07 в S3, сохраняя бакет.

В test-cycle остаются три ES-узла, новые узлы не добавляются. Mock-тесты
не заменяют облачный прогон. [Полный test-cycle опубликованного выпуска](release-cloud-acceptance.json)
подтвердил сайт, все источники логов, Kibana, повторный deploy,
сохранность документов и ID и очистку через state и API.

## Последовательное размещение

Для нового стенда используется [последовательный подбор](distributed-placement.md)
с отдельными state в `.local/stages/`. Обычный deploy продолжает незавершённый
этап и сохраняет успешные ресурсы. Контекст `.local/staged-deployment.json`
нельзя удалять до подтверждённой очистки всех пулов и Глобального роутера.
Изменение порядка пулов не переносит действующие узлы. Подключения между
пулами создаются через Глобальный роутер после подтверждения успешной ВМ,
без публичных IP на ES-узлах. Настройки запуска читаются из `.env`:
[приоритет и ограничения изменения](run-settings.md). Созданная текущей
неуспешной попыткой сеть очищается только при отсутствии использующих её ВМ
и после аудита state/API; занятые и сохранённые сети не удаляются этим шагом.

При ошибке destroy повторяется та же команда с сохранёнными служебными файлами.
Если контекст утрачен или state изменён вне контроллера, автоматическая работа
блокируется до явного восстановления привязки. Прежний state одного пула
не преобразуется автоматически в последовательный: его удаление и новый
стенд являются отдельными операциями.
