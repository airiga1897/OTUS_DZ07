# Подбор размещения Selectel

Предпочтения пулов, маски типов дисков и параметры ВМ задаются в `.env`,
по образцу [.env.example](../.env.example). Сначала проверяются `ru-2`,
`ru-9` и `ru-3`, затем остальные совместимые пулы API.
Явные исключения пулов и сегментов перечислены в [настройках запуска](run-settings.md).
Сетевые соответствия находятся в [config/placement.json](../config/placement.json).
Размещение действующего стенда сохраняется.

[Результаты проверки каталогов через API](pool-catalog-audit.md) объясняют
конкретные причины исключения пулов. Доступный каталог не доказывает наличие
свободных физических хостов; новых ВМ при этой проверке не создавалось.

## Вычислительный сегмент и сеть

Сегмент ВМ, сегмент диска и зона планирования сетевых служб — отдельные параметры.
Их имена не обязаны совпадать. По документации Selectel приватная сеть ограничена
проектом и пулом; внутри пула обеспечивается L2-связность.

API объявляет вычислительные и дисковые сегменты `ru-3a` и `ru-3b`, но зону
планирования сети и обычного облачного маршрутизатора — `ru-3a`. Поэтому для
`ru-3b` в конфигурации задано явное соответствие `network_placement`:
ВМ и диски находятся в `ru-3b`, сеть и маршрутизатор используют `ru-3a`.
Соответствие ограничено одним пулом, снабжено ссылкой на документацию провайдера
и проверяется по актуальным каталогам API. Сопоставления по суффиксам нет.
Для остальных сегментов адаптер сначала выбирает точный доступный сетевой
домен из API; если его нет — единственный обычный домен того же пула.
Для сети и маршрутизатора это проверяется отдельно: например, общая сеть
может объявляться как `ru-6a`, а маршрутизатор — как `ru-6b`.
Домены `*-paas`, чужие пулы и неоднозначные варианты автоматически не выбираются.
Явное `network_placement` имеет приоритет и тоже проверяется по API.
Разные узлы могут выбираться в разных пулах через [Глобальный роутер](distributed-placement.md);
это создание очередного узла, а не перенос существующей ВМ.

Terraform получает отдельные `availability_zone`, `network_availability_zone`
и `router_availability_zone`. Различающиеся значения включаются в привязку
state и контекста. После создания проверяются фактический сегмент каждой ВМ,
зоны сети и маршрутизатора, фильтрация портов и разнесение узлов.

## Типы дисков и маски

Учтено ограничение выбора дисков, ранее выявленное в ДЗ05–ДЗ06: наличие типа
диска в пуле `ru-3` не означает его доступность во всех сегментах этого пула.
В ДЗ07 это проверяется самостоятельно, без чтения соседних проектов.

| Сегмент | Universal SSD | Basic SSD |
| --- | --- | --- |
| `ru-3a` | `universal.ru-3a` | Не объявлен в каталоге |
| `ru-3b` | `universal.ru-3b` | `basicssd.ru-3b` |
| `ru-9a` | `universal.ru-9a` | `basicssd.ru-9a` |

Порядок масок — `universal.*`, затем `basicssd.*`. Маска отбирает названия
из каталога; параметр `RESKEY:availability_zones` в `extra_specs` подтверждает
привязку к выбранному сегменту. Например, для `ru-3a` нельзя подставить
`basicssd.ru-3b`. Маска `universal.*` не включает другой класс `universal2.*`.

Если подходящего Universal нет, проверяется разрешённый Basic SSD того же
сегмента. Неизвестная привязка, несовместимый сегмент или отсутствие разрешённых
типов исключают вариант с объяснением. Ошибка API не считается отсутствием типа.
HDD и другие классы автоматически не добавляются. Названия и доступность
повторно читаются из API перед новым развёртыванием.

Сообщение об исключении пула перечисляет отсутствующие публичные HTTPS API.
Для образа указываются число подходящих имён и отклонённые поля, включая
`checksum`; для диска — разрешённые маски и объявленные привязки типов.
Ошибки квот называют ресурс (`compute.ram`, `volume.gigabytes`, `network.port`),
а не только общую нехватку ресурсов. Неизвестный ответ и ошибка доступа
не трактуются как отсутствие поддержки.

## Диагностика ошибки до очистки

При ошибке развёртывания до удаления ресурсов создаётся отдельный обезличенный
отчёт `docs/placement-faults/<этап>-<идентификатор>.json`.
[Сборщик диагностики](../scripts/placement_diagnostics.py) читает только ВМ,
принадлежность которых подтверждена собственным state и проектом.
В отчёт входят статус, полный доступный объект `fault` с `code`, `message`,
`details`, состояния Nova и ошибка Terraform. Реквизиты и прикладные секреты
маскируются. Отчёт остаётся после удаления служебных файлов стенда.

Ответы `403`, `404`, отсутствие `fault` и сетевые ошибки отмечаются отдельно;
они не подменяются выводом о нехватке ресурсов. Недоступность диагностики
не останавливает обязательную очистку временного стенда. Следующий вариант текущего узла допускается только после подтверждения
удаления неуспешной попытки через её state и API; успешные этапы сохраняются.
Ошибка повторного применения действующего стенда не запускает его удаление.

## Подтверждение

Образ выбирается по точному названию `Ubuntu 24.04 LTS 64-bit` и явному списку
MD5 из поля `image_checksums` в [конфигурации](../config/placement.json).
Glance `checksum` содержит MD5. Разрешены текущая сборка и сборка ru-2 от
14.04.2026. Обе имеют `os_distro=ubuntu`, `min_disk=5`, `min_ram=512`;
проверяются также публичность, состояние `active`, архитектура и соответствие
ресурсам выбранного профиля. Произвольная сборка по одному имени не допускается.
ru-4 и ru-5 исключены: точного образа в проверенных каталогах не найдено.
Работа ролей на сборке ru-2 подтверждена полным
[test-cycle в ru-2a](ru2-test-cycle-summary.json) без перехода в другие пулы.

Маски сохраняют порядок предпочтений типов при разных именах в каталоге,
а раздельные зоны позволяют учитывать `ru-3b`, не требуя совпадения его имени
с зоной планирования сети. Подтверждены следующие совместимые сочетания:

| Вычислительный и дисковый сегмент | Зона сети | Зона маршрутизатора | Выбранный тип диска |
| --- | --- | --- | --- |
| `ru-9a` | `ru-9a` | `ru-9a` | `universal.ru-9a` |
| `ru-3a` | `ru-3a` | `ru-3a` | `universal.ru-3a` |
| `ru-3b` | `ru-3a` | `ru-3a` | `universal.ru-3b` |

Совместимость этих сочетаний подтверждена каталогами API и правилами Selectel.
Она не означает, что создание полного стенда уже прошло успешно.

[placement-candidates.json](placement-candidates.json) фиксирует результат запросов
на чтение: `ru-9a`, `ru-3a`, `ru-3b`, отдельные сетевые зоны и Universal-диски.
Локальные тесты проверяют маски, привязку дисков, разделение зон, сохранение
контекста, подробного `fault` и порядок «диагностика → очистка».
Terraform mock-план проверяет ВМ и диски в `ru-3b` при сети в `ru-3a`.

Это подтверждает подбор по контрактам провайдера, но не свободные физические
хосты или фактическую связность новых ВМ. Полный облачный прогон исправленного
варианта требует отдельного разрешения. Его результат не следует выводить
из положительных квот или наличия конфигурации в каталоге.
