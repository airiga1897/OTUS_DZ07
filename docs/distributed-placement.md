# Последовательное размещение между пулами Selectel

`deploy` создаёт общую ВМ и три Elasticsearch последовательно. Для каждого
узла независимо перебираются совместимые кандидаты: сначала `ru-9 → ru-3`,
включая `ru-3b`, затем остальные пулы из API. `ru-7` исключён для ВМ.
Предпочтения не образуют закрытый список. Диски выбираются по маскам Universal → SSD.
Сеть и маршрутизатор имеют собственные зоны планирования; после создания
они сохраняются и повторно используются следующими узлами своего пула.

[Причины выбора и порядок создания в ADR](adr/0001-retained-placement.md).

## Устройство

[Настройки запуска](run-settings.md) содержат предпочтения пулов, параметры ВМ
и маски дисков. [Политика сети](../config/placement.json) задаёт порядок узлов,
диапазон автоматического выделения и явные подсети:

| Пул | Подсеть |
| --- | --- |
| ru-9 | 10.77.0.0/24 |
| ru-3 | 10.78.0.0/24 |

Для остальных совместимых пулов контроллер выбирает свободные /24 из
`sequential_placement.subnet_pool`, проверяя пересечения. Выбор детерминирован
именем пула и зафиксирован в контексте до первого создания. Сами сети создаются
только при попытке разместить ВМ. После начала стенда список подсетей не расширяется
автоматически по изменившемуся каталогу или `.env`.

Обычный облачный роутер использует адрес `.1` для выхода в Интернет.
Глобальный роутер использует `.2`, служебные порты — `.253` и `.254`.
DHCP выделяет адреса `.200–.249`; адреса ВМ задаются явно вне этого диапазона.
Все смещения находятся в одном разделе `sequential_placement.addresses`.
До создания проверяются пересечения адресов, подсетей и резервов.

Сеть создаётся при первом обращении к пулу, затем — порт, диск и ВМ.
После подтверждения `ACTIVE` сохраняются ID ВМ и создаются Глобальный роутер
и подключение подсети. Ошибка подключения сохраняет успешную ВМ для повторного
deploy. Уже созданный Глобальный роутер используется при подключении следующего пула.
Маршруты удалённых подсетей задаются в Neutron через локальный шлюз
Глобального роутера. В одном пуле ВМ используют приватную сеть напрямую.
Правила межпулового доступа задаются только для собственных подсетей проекта.
SSH остаётся на порту 22 с подтверждённых публичных /32; публичный IP есть
только у app. Приватный транспорт Elasticsearch использует TLS.

Перед выделением ресурсов проверяются каталоги, образ, привязка конфигурации
ВМ и диска к сегменту, обязательные возможности сети и маркировки ресурсов, квоты и конфликты адресов.
Проверка квот ищет допустимое сочетание для всех оставшихся узлов между пулами.
Для Глобального роутера API должен подтвердить VPC-зоны, общую группу зон
и достаточные квоты роутеров, сетей и подсетей. Неизвестная схема ответа,
отсутствующая квота или ошибка доступа останавливают запуск до выделения
ресурсов. Каталог и положительная квота не доказывают наличие физических хостов.

## Сохранение ресурсов и повторный запуск

[Общий порядок этапов](../scripts/staged_deploy.py) не зависит от API провайдера.
[Адаптер Selectel](../scripts/selectel_staged.py) подбирает размещение,
а [отдельные Terraform-модули](../terraform-selectel/staged/) описывают сеть,
Глобальный роутер, подключение подсети и ВМ.

Каждый этап имеет отдельный Terraform state в `.local/stages/<этап>/`.
Атомарно сохраняемый `.local/staged-deployment.json` связывает этапы с проектом,
namespace, ID запуска, размещением, ID ресурсов и lineage state. Он также
содержит данные незавершённой попытки. Эти файлы не публикуются.
Операции одного локального клона, включая полный test-cycle и очистку,
защищены блокировкой ОС. После очистки остаётся несекретный файл-мьютекс
`.local/stage-operation.lock`; контекста стенда он не содержит.
Одновременные запуски разных клонов с одним namespace в одном аккаунте Selectel
не предусмотрены: для них нужны разные имена ресурсов и подсети.

При нехватке физических хостов сохраняется полный доступный `fault`.
Удаляется только неуспешная попытка текущего узла. Новый кандидат допускается
после подтверждения отсутствия ресурсов этой попытки через state и API.
Успешные ВМ, используемые сети и подключения остаются. Вновь созданная сеть
неудачной попытки удаляется после проверки отсутствия собственных ВМ в ней
и подтверждения очистки state/API. Сохранённая сеть из предыдущего запуска
не считается новой временной сетью; её данные восстановления сохраняются.

Неопределённая ошибка не запускает автоматическое удаление. После исправления
причины повторный `deploy` продолжает сохранённую попытку. Подтверждённая
ошибка NoValidHost незавершённой ВМ обрабатывается как неуспешный кандидат.
Повторный deploy действующего стенда использует сохранённые параметры,
не перечитывая предпочтения как разрешение перенести узлы.
План разрешает создание новых ресурсов и отсутствие изменений существующих;
замена, изменение, удаление и смена ID блокируются.
Адаптер отдельно проверяет обновление вычисляемых сведений API: пустые
списки меток, служебные метки сохранённого подключения Глобального роутера
и список членов группы разнесения. При включённом разнесении он должен точно
соответствовать собственным действующим ES-узлам из state; в диагностическом
режиме ES в группу не включаются. Это не разрешает Terraform менять
существующие ресурсы; неизвестные метки, чужие участники и изменение политики
разнесения блокируются.
При утрате контекста, изменении lineage или несовпадении ID автоматическая
работа останавливается; state, контекст и ключи необходимо сохранить.
Зависшую блокировку Terraform нельзя снимать, пока не проверено отсутствие
действующего процесса Terraform и другого оператора.

## Настройка и проверки

Общий контроллер не интерпретирует пулы, зоны или ошибки API. Он вызывает
фабрику выбранного адаптера, получает порядок этапов и непрозрачные кандидаты.
Selectel самостоятельно формирует альтернативы и определяет условия повтора;
у другого провайдера этот алгоритм может быть иным.

Общий результат инфраструктуры содержит роль, ID, адрес, подсеть, пул и сегмент
каждого узла. Из него формируется inventory Ansible. Роли PostgreSQL, Nginx,
Django, HAProxy, Elasticsearch, Kibana и Filebeat не обращаются к API Selectel.
Для другого облака заменяются адаптер связности и Terraform-ресурсы;
поддержку соответствующей сети потребуется подтвердить отдельно.
Другой провайдер в этом проекте не реализован.

После создания проверяются фактические сегменты ВМ, зоны сети и роутеров,
адреса и фильтрация портов, маршруты, принадлежность подключений Глобального
роутера и, в обычном режиме, физическое разнесение трёх ES-узлов. Между пулами разнесение
проверяется по паре «пул, hostId», внутри пула — также по обязательной группе
anti-affinity. SSH между приватными адресами, формирование ES-кластера,
поступление журналов и запросы Kibana проверяются обычными configure/verify.

Пользовательские команды из [README](../README.md) сохраняются:
`deploy`, `verify`, `open`, отдельный `destroy` и временный `test-cycle`.
`open` сверяет локальные ID ВМ, дисков и портов, показывает размещение каждого
узла и URL без облачной авторизации.

## Доступ

Один сервисный пользователь использует прежний ввод через `env.ps1`:
`member` в своём проекте для облачных ресурсов и `global_router.admin`
в области аккаунта для Глобального роутера. Для подключения сетей нужны
обе роли. Пользователь получает права уровня аккаунта на эту услугу;
ограничение конкретным namespace выполняется кодом и не является IAM-изоляцией.

Из одной схемы реквизитов выпускаются токен проекта для OpenStack и токен
аккаунта для Глобального роутера. Они живут в памяти, в файлы не сохраняются.
Terraform получает реквизиты только из окружения дочернего процесса.
S3-ключи доставки файлов для этих API не используются.

## Удаление

`destroy` удаляет ВМ, затем подключения, сети пулов и Глобальный роутер.
Ошибка одного этапа не отменяет попытки очистить остальные. В конце проверяются
все stage state, все использованные пулы и собственные объекты Глобального
роутера, включая объекты с меткой запуска, не найденные в state.
Повторное удаление допускает отсутствие объектов, уже удалённых предыдущей
подтверждённой попыткой, без разрешения чужих изменений state.

Только после полного аудита удаляются служебные файлы. При ошибке сохраняются
state, журнал этапов, ключи и секреты. Реквизиты разработки удаляются отдельно.
`destroy --purge-artifacts` после удаления стенда очищает согласованный префикс
S3 и сохраняет бакет. `test-cycle` допускается только без контекста и stage state,
а в finally вызывает тот же аудит удаления только собственного тестового стенда.

## Подтверждение и ограничения

Реализация проверяется локальными mock-тестами контроллера и Terraform.
Сценарии проверяют переход между пулами после ошибки, сохранение ID,
возобновление, повторное применение, ограничения планов, квоты и аудит очистки.
Это не подтверждает действующие права аккаунта, фактическую межпуловую
связность или работу кластера в Selectel. Для этого нужен отдельный облачный
прогон. Исходный legacy state одного пула автоматически не преобразуется:
он обслуживается прежним путём до отдельного удаления.
