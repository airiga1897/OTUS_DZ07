# Дополнительные сценарии Elasticsearch

Повторно используемые механизмы управления инфраструктурой, развиваемые в серии
учебных проектов, выделены в дополнительные эксплуатационные сценарии.
Они предназначены для проверки отказоустойчивости и дальнейшего расширения
проекта и не входят в обязательный `test-cycle`.

Команды выполняются в PowerShell из корня клона после обычного `deploy`,
на полностью настроенном действующем стенде. Реквизиты загружаются через
`scripts/env.ps1` тем же способом, что для обычного управления стендом.
Для доставки текущих исходников сохраняется выбранный режим S3 или Releases.

## Проверка отказоустойчивости ES

**Команда временно выключает одну ВМ Elasticsearch.** ВМ app, PostgreSQL,
Nginx, HAProxy и Kibana не выключаются.

```powershell
.\.tools\venv\Scripts\python.exe scripts/lab.py verify --es-failover
```

Контроллер проверяет штатное состояние кластера, определяет текущий master
и сверяет его с собственными master-eligible узлами. Пул и ID ВМ берутся из
сохранённого результата инфраструктуры; используется адаптер API этого пула,
даже если app находится в другом пуле.

Перед выключением в `.local/es-failover.json` атомарно сохраняется привязка
к стенду, проекту, пулу и ВМ. Проверяются автоматическая смена master,
сохранность контрольного документа и запись при недоступном узле.
В завершающем блоке всегда предпринимается включение исходной ВМ и проверка
возврата полного состава и состояния `green`. Ошибка проверки не отменяет
восстановление; ошибка восстановления не заменяет первоначальную причину.
Число попыток задаётся в [несекретной конфигурации](../config/optional-elasticsearch.json).
После восстановления выполняются обычные проверки сайта, логов и Kibana.

При недоступности управления восстановление не объявляется успешным.
Контекст сохраняется, обычные deploy/configure/verify и запрос es4 блокируются.
После восстановления связи повторяется **та же команда**: при наличии маркера
она только восстанавливает сохранённую ВМ, не выключая новый master.
При перезапуске контроллера действует тот же порядок. При несовпадении привязки
работа блокируется. Обезличенный результат `docs/elastic-failover.json` создаётся
при выполнении команды; его отсутствие до запуска является штатным.

## Подключение es4

**Команда создаёт дополнительную ВМ и диск** для настроенного существующего стенда.

```powershell
.\.tools\venv\Scripts\python.exe scripts/lab.py add-es4
```

es4 получает роли `data` и `ingest`; master-eligible остаются es1–es3.
Имя, роль и смещение частного адреса определены в
[optional-elasticsearch.json](../config/optional-elasticsearch.json).
Базовый [topology.json](../config/topology.json) остаётся из четырёх ВМ.

Сначала фиксируются контрольные данные, документы Elasticsearch и ID ресурсов.
Запрос расширения сохраняется в контексте стенда до создания ресурсов.
Подбор использует существующие правила размещения и неизменные параметры
сохранённых ВМ. Terraform-планы проверяются до apply; замена и удаление
действующих ресурсов запрещены. Существующие данные не переинициализируются,
фикстура повторно поверх пользовательских данных не загружается.

После создания Ansible присоединяет узел к существующему кластеру через
discovery и TLS, без первоначального bootstrap нового кластера. Проверяются
состав кластера, сохранность документов и ID, приложение и логи нового узла.
При ошибке существующий стенд автоматически не удаляется: state, запрос,
частично созданный es4 и диагностические данные сохраняются для продолжения.

Повторный `add-es4` или обычный `deploy` продолжает сохранённый запрос.
После успешного расширения дальнейший deploy сохраняет пять ВМ и не добавляет
es4 повторно. Изменение базовой топологии, роли или адреса сохранённого узла
требует отдельного сценария. Удаление всего стенда выполняется обычным `destroy`.

## Область проверки

Обычный `verify` не выключает ВМ и не добавляет узлы. Временный `test-cycle`
не вызывает эти сценарии и отклоняет топологию с es4 до создания ресурсов.
Он запускается только без действующего стенда и очищает собственные ресурсы.

Новые дополнительные сценарии проверены локально с mock API, изолированными
контекстами и настоящим контроллером этапов. Подтверждены выбор пула,
восстановление после ошибок, продолжение по маркеру и добавление без повторного
создания существующих узлов. Облачная работоспособность es4 и проверки
отказоустойчивости этой реализации пока не подтверждена.
Ранее успешный [test-cycle ru-2a](ru2-test-cycle-summary.json) относится
к обычной схеме без es4 и выключения ВМ.
