# ДЗ07-ADR-0001. Сохранение этапов при межпуловом подборе

**Статус:** Принято для ДЗ07.

## Контекст

Нехватка физических хостов для одной ВМ не требует удалять уже созданные
узлы. В Selectel приватные сети разных пулов связываются Глобальным роутером.
Один общий параметр зоны не описывает такое размещение.

## Решение

Хранить отдельный state для сети каждого использованного пула, Глобального
роутера, подключения подсети и каждой ВМ. Общий контроллер задаёт порядок
и правила сохранения этапов. Адаптер Selectel проверяет каталоги и граф сети,
область реквизитов, квоты, размещение и аудит удаления.
Ansible получает общий результат с размещением и адресами каждого узла.

Реквизиты определяются прежней схемой. Токены аккаунта и проекта выпускаются
из одного окружения. Подсети не пересекаются; DHCP и служебные адреса отделены
от фиксированных адресов ВМ. Все резервы задаются одной конфигурацией.

Неуспешная попытка нового узла очищается отдельно после сохранения fault.
Следующий кандидат допускается только после подтверждения очистки через
state и API. Ошибка настройки сохраняет стенд. Полный destroy аудирует
каждый пул и Глобальный роутер до удаления локальных данных восстановления.

## Порядок создания

1. Получить блокировку клона и подтвердить отсутствие чужого или незавершённого
   стенда для нового test-cycle. Подтвердить публичный /32 оператора.
2. До выделения ресурсов проверить проект, API, каталоги, привязки сегментов,
   диски, конфигурации ВМ, квоты, непересекающиеся подсети, группу зон
   Глобального роутера и возможность маркировки собственных ресурсов.
3. Сохранить журнал подготовки, ключи и секреты приложения; подготовить
   доставку исходников и пакетов с проверкой хешей.
4. Последовательно размещать app, es1, es2, es3. Для очередного кандидата
   создать или использовать сеть его пула, затем порт, диск и ВМ текущего этапа.
   После подтверждения ACTIVE сохранить ID узла и создать подключение подсети
   к одному Глобальному роутеру. Ошибка подключения сохраняет успешную ВМ.
5. При подтверждённой нехватке хостов сохранить fault и удалить только
   неуспешную попытку узла. После аудита state/API перейти к следующему
   кандидату этого узла. Вновь созданную неиспользуемую сеть очищать отдельно
   с аудитом; сеть успешной ВМ и сохранённые этапы не пересоздавать.
6. После получения всех узлов подтвердить реальные размещение, маршруты,
   фильтрацию и выбранный режим разнесения ES; сформировать общий результат инфраструктуры
   и inventory, применить Ansible и проверить службы.
7. При повторном deploy сверить ID и lineage, использовать сохранённые
   размещения и применить настройки служб без изменения инфраструктуры.
8. При отдельном destroy удалить узлы, подключения, сети и роутер с аудитом
   всех этапов. Временный test-cycle вызывает эту очистку в finally.

Если удаление узла завершилось ошибкой, продолжать очистку других узлов.
Подключение его пула и сеть сохраняются, пока удаление дочерних этапов не
подтверждено state и API. Сеть дополнительно ожидает удаления подключения;
Глобальный роутер — всех подключений. Независимые пулы продолжают очищаться.
Неизвестное размещение узла блокирует все потенциальные родительские этапы.
К неизвестному относятся также повреждённая запись кандидата, нестроковый пул
и пул без соответствующих сохранённых родительских этапов. Это не разрешает
удаление по догадке и не ослабляет проверку области журнала.
Это предотвращает ожидание удаления сети, ещё занятой собственным узлом.
Повторный destroy использует прежние state и контекст и завершает удаление
в порядке зависимостей, затем подтверждает отсутствие ресурсов через API.

## Причины выбора

Отдельный state ограничивает Terraform-план ресурсами конкретного этапа.
Это позволяет очистить неуспешную ВМ, не включая действующие узлы в план
удаления. Проверка плана и сохранённых ID дополнительно блокирует замену
и изменение ресурсов. Журнал связывает отдельные state в один стенд и
сохраняет сведения для восстановления после прерывания.

Создание собственных узлов и подключений меняет вычисляемые сведения API:
членство в группе разнесения и служебные метки сети. Адаптер Selectel сверяет
их с сохранёнными связями, составом собственных ВМ и выбранным режимом разнесения. Это позволяет
продолжать последовательное создание без ослабления запрета на изменение
ресурсов: неизвестные расхождения и любые изменяющие действия Terraform
для существующих ресурсов остаются запрещены.

Создание сети при первом использовании пула сохраняет возможность подобрать
следующий узел независимо. Глобальный роутер даёт приватную связность между
такими сетями через поддерживаемые API и Terraform. Его ID и уже созданные
подключения сохраняются при дальнейшем подборе. Подключение создаётся только
после успешной ВМ, поэтому не выделяется для неудачного кандидата. Вновь созданная
неиспользуемая сеть удаляется с аудитом; сеть действующей ВМ сохраняется.

Настройка служб начинается после размещения всех узлов. До этого перебор
кандидатов не затрагивает прикладные данные или уже сформированный кластер.
После настройки автоматический перенос и замена узлов запрещены.

Общий слой получает кандидата как непрозрачный набор параметров. Он не
сопоставляет пулы и зоны и не распознаёт строки ошибок конкретного API.
Адаптер предоставляет порядок этапов и кандидатов, проверяет совместимость,
определяет допустимость повтора, создаёт ресурсы и доказывает их очистку.
Поэтому другой провайдер может использовать собственный алгоритм подбора.
Типы ресурсов, endpoint, реквизиты доступа и переменные окружения не
переносятся на него по предположению. Сейчас реализован только Selectel;
новый провайдер добавляется отдельной задачей с независимым state и проверками.

## Последствия

Неуспешная команда Terraform сохраняет обезличенную диагностику с уникальным
именем до запуска очистки. Исходный вывод фиксируется непосредственно на
границе запуска команды: последующий `destroy` не заменяет его своим выводом.
Отчёт содержит этап, операцию и привязку к тестовому запуску. Обезличенные
доказательства сохраняются после удаления state и служебных журналов.
Сведения API о состоянии собственных ресурсов собирает адаптер провайдера;
недоступная диагностика не заменяет исходную ошибку и не блокирует очистку.

Успешные ресурсы сохраняют ID, данные и размещение. Локальные проверки
наблюдаемых полей OpenStack сверяют первоначальную привязку порта
и floating IP с сохранёнными ID, сетью, адресом и владельцем.
Поля DNS и неизвестная QoS-политика допускаются только при первоначальной
привязке порта. Обновление наблюдаемого состояния не разрешает Terraform
изменять существующие ресурсы: их план должен оставаться `no-op`.
Регрессионный пример содержит обезличенные формы полей облачного плана;
конкретные значения в нём синтетические.

Используются несколько локальных state и обязательный журнал этапов. Сохранённые сети прерванного
запуска остаются учтёнными до восстановления или destroy. Дополнительная роль Глобального роутера имеет
область аккаунта; ограничение namespace реализовано кодом.

Локальные mock-тесты подтверждают управление этапами, но не облачную связность.
Другие ДЗ и реализации других провайдеров этим решением не изменяются.
