# ДЗ07-ADR-0007: границы решения и повторного использования

Статус: принято для документации реализованного решения.

## Контекст и границы задания

ДЗ07 требует минимум три узла Elasticsearch, сбор журналов веб-серверов,
БД и балансировщиков, обработку событий и подтверждение их поступления.
Kibana — дополнительный пункт задания. Реализованная основа — три отдельных
ES-узла и app с Nginx, Django/uWSGI, PostgreSQL, HAProxy, Kibana и Filebeat.
Эксплуатационные механизмы ниже не объявляются обязательными для минимального ДЗ.

Дефицит хостов, несовместимые сочетания и частичные операции требуют
сохранения успешно созданных ресурсов и данных восстановления. Эти механизмы
не гарантируют доступность следующего кандидата. [Подтверждённый облачный
цикл](../current-cloud-acceptance.json) использует один пул; другие сочетания
и намеренный обрыв связи подтверждаются отдельно.

## Выбор и рассмотренные альтернативы

| Причина | Выбранное решение | Альтернатива и граница выбора |
| --- | --- | --- |
| Дефицит доступных ресурсов и несовместимые сочетания сети, дисков, образов и ВМ | Последовательная проверка полных кандидатов с сохранением успешных этапов | Один фиксированный пул проще, но сужает выбор; последовательный подбор всего стенда в одном пуле также проще, однако не использует уже согласованное межпуловое размещение. Алгоритм не создаёт отсутствующую ёмкость. |
| Размещение узлов в разных пулах | Приватные сети через Глобальный роутер Selectel | Один пул обходится без него. Публичные соединения не заменяют выбранную приватную связность. Межпуловая связность требует отдельного облачного подтверждения. |
| Потеря связи с локальным контроллером | Ansible на app в systemd, сохранённый ID и возобновление наблюдения | Запуск в SSH-сессии проще, но зависит от неё. Постоянный внешний оркестратор добавил бы отдельный сервис, который заданием не требуется. |
| Частичное создание и ошибки удаления | Учёт намерений и попыток, отдельные state, сохранённый контекст и аудит через API | Безусловный destroy при любой ошибке опасен для действующего стенда. Один state и фиксированное размещение проще, но не дают выбранной независимости этапов. Имя ресурса и выделенный проект сами по себе не разрешают удаление. |
| Самостоятельное развёртывание проверяющим | Версионированные GitHub Releases и проверка SHA512 | Наш приватный S3 требует чужого доступа, а загрузка напрямую с сайта Elastic зависит от его доступности по маршруту ВМ. S3 сохранён как явно выбранный способ доставки для разработки, без автоматического fallback. |

## Последствия и цена

Повторное применение сохраняет действующие ресурсы и данные; временное полное
испытание отделено от эксплуатации. Вместе с этим увеличиваются объём кода,
число состояний, количество служебных файлов, матрица отказных проверок и
сложность сопровождения. Для межпулового размещения требуются права Глобального
роутера; во всех режимах необходимо аккуратное
сохранение данных восстановления. Неизвестный результат API или неполный аудит
не превращаются в успешную очистку. Наличие этих механизмов и высокий процент
покрытия не доказывают отсутствие ошибок и не гарантируют доступность облака.

Пользовательский путь остаётся коротким: `env.ps1 → deploy → verify → open → destroy`.
Предварительные проверки входят в deploy. Отдельный preflight проверяет
доступность и размещение без создания ресурсов. Обычные verify и test-cycle
не добавляют es4 и не выключают узлы. Явные дополнительные сценарии описаны
в [ADR-0005](0005-optional-elasticsearch.md).

## Повторное использование и подтверждение

| Слой | Реализация в этом репозитории | Что потребуется следующему проекту |
| --- | --- | --- |
| Создание ресурсов Selectel | [Terraform](../../terraform-selectel/staged), [адаптер](../../scripts/selectel_adapter.py), [этапы Selectel](../../scripts/selectel_staged.py) | Каталоги, авторизация и ресурсы другого облака реализуются отдельно. |
| Порядок этапов и жизненный цикл | [staged_deploy.py](../../scripts/staged_deploy.py), [staged_runtime.py](../../scripts/staged_runtime.py) | Проверить контракты владения, повторного применения и очистки для новой инфраструктуры. |
| Настройка служб | [Ansible-роли](../../ansible/roles) | Подтвердить ОС, параметры сети и дисков, входные данные inventory. |
| Проверки данных и служб | [verification.py](../../scripts/verification.py), [observability.py](../../scripts/observability.py) | Адаптировать проверки к требованиям приложения и отдельно испытать их в облаке. |

Terraform создаёт инфраструктуру конкретного облака. Адаптер Selectel отвечает
за его авторизацию, каталоги, размещение, возможности и аудит. Ansible получает
общий состав узлов и настраивает службы; проверки оценивают данные и состояние
сервисов. Эти границы позволяют повторно использовать роли и порядок этапов
при подтверждённых одинаковых требованиях к ОС, сети и хранилищу.

Это основа для следующих проектов, а не готовый многопровайдерный runtime.
Другой провайдер потребует своего Terraform-модуля, авторизации, адаптера API,
проверок обязательных свойств и независимого облачного испытания. Поддержка
другого облака сейчас не реализована; универсальный фреймворк не создаётся.

[Текущий облачный цикл](../current-cloud-acceptance.json) подтверждает первый
и повторный запуск Ansible через systemd и отображение задач. [Локальный
набор](../local-quality.md) проверяет ошибки и восстановление с подставными API
и транспортами. Намеренный обрыв реальной сети в облаке не испытывался.
