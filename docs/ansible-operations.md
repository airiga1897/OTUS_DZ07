# Выполнение Ansible и восстановление связи

Команды `deploy`, `verify`, `open`, `destroy` и `test-cycle` сохраняются.
Настройка через `deploy` выполняется на app во временном сервисе systemd,
независимом от SSH-сессии оператора. Один запуск получает случайный ID.
Повторное подключение или повторный `deploy` не создают заменяющий запуск.

## Состояние и повторная команда

Служебный контекст `.local/ansible-operation.json` сохраняется до возможной
отправки команды запуска. Он связывает ID операции со стендом, ID app,
контрольной суммой исходников и параметров, включая приватный inventory.
Вместо реквизитов в контекст операции записываются хеши входных файлов.

| Состояние | Значение |
| --- | --- |
| `preparing` | Операция зарезервирована, Ansible ещё не запущен |
| `running` | Сервис или его дочерние процессы ещё работают |
| `succeeded` | Получен полный атомарный результат с кодом 0; сервис завершён |
| `failed` | Получен результат с ненулевым кодом, в том числе таймаут самой операции |
| `stopped` | Явная остановка подтверждена |
| `unknown` | Связь недоступна либо результат отсутствует/повреждён; успех не подтверждён |

После обрыва связи восстановите подключение и повторите обычную команду:

```powershell
.\.tools\venv\Scripts\python.exe scripts/lab.py deploy
```

Контроллер сверит привязку и параметры, затем продолжит наблюдение за тем же
ID. Если ответ о запуске потерян, проверяется сервис с прежним именем.
Стабильное имя systemd unit и блокировка исполнителя предотвращают повторное
выполнение. После перезапуска локального контроллера работает тот же порядок.
Операция в подготовке может завершить передачу файлов с прежним ID.

До подтверждённого завершения не меняйте исходники, inventory или размещение.
Несовпадение блокирует продолжение. При повреждённом результате или перезагрузке
app неизвестный исход не превращается в автоматический повтор Ansible.
После подтверждённой ошибки Ansible и успешных завершающих действий операция
закрывается с сохранением ошибки. Следующий явный `deploy` может начать новую
операцию; автоматического повтора в вызове, получившем ошибку, нет.
Для состояния уже созданного стенда достаточно чтения локального контекста:

```powershell
$operation = Get-Content .local/ansible-operation.json -Raw | ConvertFrom-Json
$operation.request.id
$operation | Select-Object state, acknowledged, finalized, stop_confirmed
```

## Ход выполнения задач

Контроллер выводит через существующий logging имя узла, статическое название
задачи и `начало`, `ok`, `changed`, `failed` или `skipped`. Это ожидаемая форма
сообщения, а не результат облачного испытания:

```text
INFO Ansible | es1 | Install Elasticsearch | начало
INFO Ansible | es1 | Install Elasticsearch | changed
```

Используется штатный notification callback Ansible, без разбора текста консоли.
Наблюдатель доставляется вместе с исполнителем управления и сохраняется в
снимке операции. Он пишет `events.jsonl` в закрытом каталоге её ID на app.
Каталог имеет режим `0700`, файлы — `0600`. События содержат только
последовательный номер, название задачи, имя узла, вид события и результат.
Аргументы, переменные, stdout/stderr, содержимое результатов модулей и URL
не передаются. Для `no_log` скрыты и название, и результат; неразрешённый флаг
`no_log` также считается закрытым. Шаблонные, отсутствующие или небезопасные
названия заменяются нейтральной подписью; `get_name()` с подстановкой аргументов
не используется.

За запрос передаётся не более 64 событий и читается не более 64 КиБ; длина
строки ограничена 2048 байтами. За один опрос обрабатывается не более 16 порций,
чтобы отображение не вытесняло проверку состояния. При большем остатке он
читается следующим опросом; при завершении большой накопленной очереди возможен
неполный вывод в консоль, сам журнал остаётся на ВМ до удаления стенда.
Частично дописанная строка не передаётся и не сдвигает позицию.

Позиция — смещение в байтах и номер события — сохраняется в
`.local/ansible-operation.json`. Ответ сверяется с полной привязкой операции;
номера должны идти последовательно, а узел — входить в состав стенда.
После восстановления связи или перезапуска читается тот же журнал того же ID.
События сначала выводятся, затем позиция атомарно сохраняется. При аварии между
этими действиями часть сообщений может повториться. Строго однократный вывод
не гарантируется; повторный запуск Ansible из-за прогресса не выполняется.

Таймера ожидания появления прогресса нет. Временная недоступность SSH/RPC,
ошибка чтения журнала или отсутствие первых событий отображаются на уровне INFO.
Сообщение содержит последнее подтверждённое состояние: для `running` —
«операция ещё выполняется», для завершённой операции — соответствующий результат.
Повтор одинаковой причины и состояния не засоряет консоль; обычные сообщения
состояния и длительности продолжаются. Отсутствие событий само по себе не
доказывает ошибку. Если удалённый исполнитель прежней версии не сообщает причину,
контроллер также не делает предположение о подтверждённой неисправности.

WARNING выдаётся с понятной причиной: callback отключил запись после ошибки,
повреждены формат или последовательность журнала, доступ запрещён, отсутствует
компонент наблюдателя, не совпадает привязка или не сохранена позиция чтения.
Отсутствие журнала после фазы `configure` и недописанная после завершения строка
также подтверждают проблему наблюдения. Если операция завершилась раньше запуска
callback, отсутствие журнала не считается такой проблемой.
Удалённый исполнитель передаёт только разрешённый код причины, без текста
исключения, реквизитов, вывода команд и URL. Неизвестный формат ответа сообщается
как нарушение протокола. Диагностика относится к наблюдателю и не заменяет результат Ansible.
Ошибка наблюдателя не останавливает playbook и не заменяет исходную ошибку.
Если новых событий нет, остаются умеренные сообщения о состоянии и прошедшем
времени; интервал задаётся `status_interval_seconds` в
[config/logging.json](../config/logging.json). Уровень INFO показывает задачи;
`--log-level WARNING` скрывает обычный прогресс. Итоговые `state` и `exit_code`
операции остаются единственным основанием для результата настройки.
Диагностика не меняет лимит выполнения Ansible или бюджет восстановления SSH.

Механизм прогресса проверен локально с mock callback/SSH/systemd. Реальное
выполнение callback на облачной app после этого изменения не испытывалось.
Основа интерфейса — [callback-плагины Ansible 2.18](https://docs.ansible.com/projects/ansible-core/2.18/plugins/callback.html).

## Ограничения времени операции

В [config/ansible-operation.json](../config/ansible-operation.json) отдельно
заданы время работы операции, бюджет ожидания связи, интервал опроса и
ожидание остановки. По умолчанию: 1800, 120, 5 и 30 секунд соответственно.
Проверка, подготовка Ansible и применение playbook входят в лимит операции.
Systemd дополнительно ограничивает срок службы процесса с запасом на остановку.

SSH RPC и передача приватных файлов используют короткие таймауты. Бюджет
ожидания связи проверяется между попытками подключения; незавершённая
операция на app продолжает работать. Исчерпание сетевого ожидания даёт
`unknown`, а не ненулевой код Ansible. Завершающие действия повторяются отдельно;
их ошибка не маскирует первоначальный результат настройки.

## Права и диагностика

Callback записывает причину отказа в закрытый `events.unavailable` атомарно:
версия формата, этап (`initialize`, `metadata`, `write`, `unknown`), разрешённая
категория ошибки и номер последнего записанного события. В консоли показываются
этап и категория, без текста исключения, traceback, аргументов, имён файлов,
имени задачи, переменных или результатов модулей. Отсутствие прав, ошибка
ввода-вывода и неподходящий тип данных различаются. После отключения callback
последующие результаты не перезаписывают первоначальную причину.

Пустой маркер прежней версии читается как общая ошибка callback: конкретная
причина не выдумывается. Повреждённая диагностика даёт отдельное предупреждение.
Если её запись невозможна, callback пытается создать прежний пустой маркер;
сбой обоих способов не прерывает Ansible. Это защитная обработка отказа
наблюдения, а не автоматическая повторная настройка стенда.

`task.get_ds()` без словаря заменяется скрытым названием, `results: null`
не отключает callback, а неизвестная форма результата скрывается. При `no_log`
источник имени не читается. Длинные допустимые Unicode-имена записываются UTF-8
в пределах прежнего ограничения строки. Проверки охватывают эти контракты
данных, а не только выполнение строк и ветвей кода. Точная причина прежнего
облачного предупреждения по пустому маркеру не установлена; исправления и
новая диагностика проверены локально, без нового облачного запуска.
Возможность `get_ds()` вернуть `None` учтена по
[исходному коду Ansible 2.18](https://github.com/ansible/ansible/blob/stable-2.18/lib/ansible/playbook/base.py).

На app операция хранит запрос, состояние, время начала/окончания, код завершения,
снимок кода и `operation.log` в закрытом каталоге `.ansible-operations/<ID>`
внутри рабочего каталога проекта. Каталоги имеют режим 0700, приватные файлы
и результаты — 0600. Сервис работает от `otus`; необходимые привилегированные
действия выполняются существующими средствами sudo/Ansible.

Результат записывается через временный файл, fsync и атомарную замену.
Inventory, SSH-ключи и управляющие переменные читаются из приватных файлов,
значения не передаются в командной строке. Реквизиты оператора и S3 на ВМ
не отправляются. [Публичная диагностика](ansible-operation-local-verification.json)
и `docs/ansible-operation-result.json` содержат только разрешённые состояния,
фазы, время, код и ID операции, без inventory, хешей параметров и сырого журнала.

## Удаление

```powershell
.\.tools\venv\Scripts\python.exe scripts/lab.py destroy
```

До удаления любой ВМ контроллер останавливает собственную операцию через
systemd и подтверждает отсутствие дочерних процессов в control group.
Неподтверждённая остановка блокирует удаление; state, ключи и контекст остаются.
После восстановления связи повторяется `destroy`.

Обычный deploy при ошибке не уничтожает стенд. Временный `test-cycle`
сохраняет обязательную очистку своих ресурсов; если управление недоступно,
он фиксирует неуспешную очистку и оставляет данные для продолжения через destroy.
После подтверждения state и API локальные служебные данные удаляются,
реквизиты разработки сохраняются. Удаление app удаляет и приватные журналы
операций на её диске.

## Область проверки

В изолированных каталогах с mock SSH/systemd проверены потери ответа до и
после запуска, восстановление связи, перезапуск контроллера, успешный и
неуспешный результат, повреждение результата, несовпадение привязки,
параллельный запуск, таймауты, остановка дочерних процессов и порядок удаления.
Первый и повторный запуск через systemd на app подтверждены
[полным test-cycle ru-2](ru2-test-cycle-summary.json) с последующей очисткой.
Потеря связи и перезапуск контроллера проверены локальными сценариями;
намеренный обрыв реального подключения в облаке не выполнялся.
Новые облачные испытания и публикация выполняются только по отдельному согласованию.
