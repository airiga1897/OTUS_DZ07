# Выполнение Ansible и восстановление связи

Команды `deploy`, `verify`, `open`, `destroy` и `test-cycle` сохраняются.
Настройка через `deploy` выполняется на app во временном сервисе systemd,
независимом от SSH-сессии оператора. Один запуск получает случайный ID.
Повторное подключение или повторный `deploy` не создают заменяющий запуск.

## Состояние и повторная команда

Служебный контекст `.local/ansible-operation.json` сохраняется до возможной
отправки команды запуска. Он связывает ID операции со стендом, ID app,
контрольной суммой исходников и параметров, включая приватный inventory.
Вместо реквизитов в контекст операции записываются хеши входных файлов.

| Состояние | Значение |
| --- | --- |
| `preparing` | Операция зарезервирована, Ansible ещё не запущен |
| `running` | Сервис или его дочерние процессы ещё работают |
| `succeeded` | Получен полный атомарный результат с кодом 0; сервис завершён |
| `failed` | Получен результат с ненулевым кодом, в том числе таймаут самой операции |
| `stopped` | Явная остановка подтверждена |
| `unknown` | Связь недоступна либо результат отсутствует/повреждён; успех не подтверждён |

После обрыва связи восстановите подключение и повторите обычную команду:

```powershell
.\.tools\venv\Scripts\python.exe scripts/lab.py deploy
```

Контроллер сверит привязку и параметры, затем продолжит наблюдение за тем же
ID. Если ответ о запуске потерян, проверяется сервис с прежним именем.
Стабильное имя systemd unit и блокировка исполнителя предотвращают повторное
выполнение. После перезапуска локального контроллера работает тот же порядок.
Операция в подготовке может завершить передачу файлов с прежним ID.

До подтверждённого завершения не меняйте исходники, inventory или размещение.
Несовпадение блокирует продолжение. При повреждённом результате или перезагрузке
app неизвестный исход не превращается в автоматический повтор Ansible.
После подтверждённой ошибки Ansible и успешных завершающих действий операция
закрывается с сохранением ошибки. Следующий явный `deploy` может начать новую
операцию; автоматического повтора в вызове, получившем ошибку, нет.
Для состояния уже созданного стенда достаточно чтения локального контекста:

```powershell
$operation = Get-Content .local/ansible-operation.json -Raw | ConvertFrom-Json
$operation.request.id
$operation | Select-Object state, acknowledged, finalized, stop_confirmed
```

## Ограничения времени

В [config/ansible-operation.json](../config/ansible-operation.json) отдельно
заданы время работы операции, бюджет ожидания связи, интервал опроса и
ожидание остановки. По умолчанию: 1800, 120, 5 и 30 секунд соответственно.
Проверка, подготовка Ansible и применение playbook входят в лимит операции.
Systemd дополнительно ограничивает срок службы процесса с запасом на остановку.

SSH RPC и передача приватных файлов используют короткие таймауты. Бюджет
ожидания связи проверяется между попытками подключения; незавершённая
операция на app продолжает работать. Исчерпание сетевого ожидания даёт
`unknown`, а не ненулевой код Ansible. Завершающие действия повторяются отдельно;
их ошибка не маскирует первоначальный результат настройки.

## Права и диагностика

На app операция хранит запрос, состояние, время начала/окончания, код завершения,
снимок кода и `operation.log` в закрытом каталоге `.ansible-operations/<ID>`
внутри рабочего каталога проекта. Каталоги имеют режим 0700, приватные файлы
и результаты — 0600. Сервис работает от `otus`; необходимые привилегированные
действия выполняются существующими средствами sudo/Ansible.

Результат записывается через временный файл, fsync и атомарную замену.
Inventory, SSH-ключи и управляющие переменные читаются из приватных файлов,
значения не передаются в командной строке. Реквизиты оператора и S3 на ВМ
не отправляются. [Публичная диагностика](ansible-operation-local-verification.json)
и `docs/ansible-operation-result.json` содержат только разрешённые состояния,
фазы, время, код и ID операции, без inventory, хешей параметров и сырого журнала.

## Удаление

```powershell
.\.tools\venv\Scripts\python.exe scripts/lab.py destroy
```

До удаления любой ВМ контроллер останавливает собственную операцию через
systemd и подтверждает отсутствие дочерних процессов в control group.
Неподтверждённая остановка блокирует удаление; state, ключи и контекст остаются.
После восстановления связи повторяется `destroy`.

Обычный deploy при ошибке не уничтожает стенд. Временный `test-cycle`
сохраняет обязательную очистку своих ресурсов; если управление недоступно,
он фиксирует неуспешную очистку и оставляет данные для продолжения через destroy.
После подтверждения state и API локальные служебные данные удаляются,
реквизиты разработки сохраняются. Удаление app удаляет и приватные журналы
операций на её диске.

## Область проверки

В изолированных каталогах с mock SSH/systemd проверены потери ответа до и
после запуска, восстановление связи, перезапуск контроллера, успешный и
неуспешный результат, повреждение результата, несовпадение привязки,
параллельный запуск, таймауты, остановка дочерних процессов и порядок удаления.
Первый и повторный запуск через systemd на app подтверждены
[полным test-cycle ru-2](ru2-test-cycle-summary.json) с последующей очисткой.
Потеря связи и перезапуск контроллера проверены локальными сценариями;
намеренный обрыв реального подключения в облаке не выполнялся.
Новые облачные испытания и публикация выполняются только по отдельному согласованию.
