# ДЗ07 — централизованный сбор логов в Elasticsearch

Проект собирает журналы собственных веб-сервера, балансировщика, серверов БД
и Elasticsearch. Kibana предоставляет поиск и таблицу событий. Django-сайт
с материалами ДЗ01–ДЗ07 использует локальную PostgreSQL.

## Архитектура

| ВМ | Компоненты | Назначение |
| --- | --- | --- |
| `app` | Nginx, Django/uWSGI, PostgreSQL 16, HAProxy, Kibana 8.19.0, Filebeat | Сайт, БД, HTTP-вход и визуализация |
| `es1`–`es3` | Elasticsearch 8.19.0, Filebeat | Отдельный кластер master/data/ingest |

По умолчанию создаются четыре ВМ: app — 4 vCPU и 8 ГБ RAM, каждый ES — 2 vCPU и 8 ГБ RAM.
[Схема проекта](docs/architecture.md) показывает сеть и потоки данных.
HAProxy принимает HTTP на порту 80 и направляет его в локальный Nginx;
Nginx передаёт запросы Django/uWSGI. PostgreSQL слушает только loopback.
Kibana доступна на app:5601 с разрешённых /32. Patroni и etcd не запускаются.

Основа — опубликованный ДЗ06, ветка `develop`, коммит
`fcde022aebfe0d1b42eb014cf5086394d1e357b7`;
[сведения об источнике](config/upstream.json). Код включён в этот репозиторий,
runtime не читает соседние каталоги ДЗ.
Terraform создаёт инфраструктуру, Ansible настраивает службы, Python управляет
проверками и жизненным циклом; особенности Selectel выделены в адаптер.

Начальные данные подготовлены по материалам ДЗ04 и загружаются Django-фикстурой.
Миграции создают схему; постоянный маркер в БД предотвращает повторную загрузку
поверх пользовательских изменений. Media находятся отдельно от исходников.

## Соответствие заданию

- Три узла Elasticsearch: discovery, первоначальное формирование кластера,
  транспортный TLS, HTTPS и авторизация.
- Filebeat на каждой ВМ: Nginx, Django/uWSGI, HAProxy, PostgreSQL, Kibana, Elasticsearch и journald.
- Шаблон `logs-otus-*`, одна реплика, обработка HTTP-полей Nginx,
  удаление журналов через семь дней.
- Проверки источников, штатного состояния служб и кластера Elasticsearch и повторного применения конфигурации.
- Kibana на общей ВМ app с представлением данных и таблицей событий.

[Сопоставление требований и кода](docs/assignment-review.md).

## Подготовка

Команды выполняются локально в PowerShell 5.1 или 7 из корня клона.
Нужны Python 3.12, Terraform с поддержкой `terraform test` и собственный проект
Selectel. `setup.ps1` создаёт локальное окружение и копирует Terraform из PATH
или пути `-TerraformPath`. Если `.env` отсутствует, скрипт копирует
[.env.example](.env.example); существующий файл сохраняется. Облачные ресурсы
при подготовке не создаются.

Подготовка устанавливает закреплённые Terraform-провайдеры в локальное зеркало
`.tools/terraform-providers` и проверяет их по lock-файлам репозитория.
Развёртывание повторяет проверку до создания ресурсов; последующие этапы
и удаление устанавливают провайдеры с диска. При сетевом сбое загрузка
повторяется до трёх раз; ошибка контрольной суммы останавливает подготовку.
Зеркало исключено из Git и сохраняется после удаления стенда.

```powershell
.\scripts\setup.ps1

# Ввод в окружение текущей сессии, пароль скрыт
. .\scripts\env.ps1

```

Проверяющему в режиме `release` достаточно собственных реквизитов Selectel:
ключи и доступ к S3 автора не требуются. Клон с готовой привязкой выпуска
и порядок запуска описаны в [инструкции Releases](docs/releases.md).
Для отдельно выбранного режима разработки `s3` дополнительно выполняется
`. .\scripts\env.ps1 -Artifacts`.

Сервисному пользователю Selectel нужны права управления вычислениями, дисками
и сетью своего проекта (`member`), а также `global_router.admin`
в области аккаунта для Глобального роутера. Последняя роль даёт доступ
к этой услуге всего аккаунта; код дополнительно ограничивает операции
собственными ID и меткой запуска. Номер аккаунта, UUID проекта и имя пользователя берутся
в панели Selectel; пароль задаётся сервисному пользователю в IAM.
Параметры ВМ, предпочтения пулов, исключения и маски дисков задаются в `.env`
в корне клона. Значения по умолчанию описаны в [.env.example](.env.example).
Сначала проверяются ru-2, ru-9 и ru-3, затем остальные совместимые пулы API;
ru-7 исключён для ВМ и разрешён для S3. ru-4 и ru-5 исключены из-за отсутствия
точного требуемого образа. ru-6 исключён из-за отсутствия разрешённых типов
дисков, ru-1b — из-за отсутствия подходящего диска в сегменте.
Список разрешённых Glance MD5 хранится в
`config/placement.json`. Сборка ru-2 проверена полным test-cycle: сайт, логи,
Kibana, повторный deploy и удаление; [результат](docs/ru2-test-cycle-summary.json). Дополнительные подтверждённые /32,
сетевые соответствия и диапазон подсетей задаются в
[config/placement.json](config/placement.json). Совместимость размещения, квоты
и отсутствие конфликтов подсетей проверяются до создания ресурсов.
Общая ВМ и каждый ES-узел подбираются последовательно и независимо;
успешные этапы сохраняются при переходе следующего узла в другой пул.
[Межпуловая связность, восстановление и доступ](docs/distributed-placement.md).
[ADR](docs/adr/0001-retained-placement.md) фиксирует порядок создания,
причины выбора отдельных state и границу общего кода и адаптера провайдера.

Настройки читаются в порядке: `.env.example` → `.env` → переменные текущей
сессии; последнее заданное значение имеет приоритет. Файл `.env` исключён
из Git и не содержит реквизитов доступа. Формат — буквальные `ИМЯ=значение`,
комментарии отдельными строками; команды и подстановка переменных не выполняются.
[Описание параметров и сохранения размещения](docs/run-settings.md).

`REQUIRE_DISTINCT_HOSTS=true` включает разнесение ES по физическим хостам.
Для отдельно согласованного диагностического стенда можно задать `false`:
блок `scheduler_hints` не передаётся, а отчёт отмечает разрешённое совместное
размещение. Такой прогон не подтверждает отказоустойчивость к потере хоста.
Режим, параметры ВМ и дисков действующего стенда менять нельзя; предпочтения
пулов не разрешают перенос или повторное создание его ресурсов.

Типы дисков выбираются по маскам `universal.*`, затем `basicssd.*`, с проверкой
привязки к сегменту через API. Для `ru-3b` вычислительный сегмент и зона
планирования сети задаются отдельно. Подробности и ограничения дисков `ru-3`:
[подбор размещения](docs/placement.md).

Отдельный режим разработки `s3` требует собственного приватного S3-бакета и трёх
проверенных пакетов. Подготовка и права: [доставка файлов](docs/artifacts.md).
Для сдачи реализован отдельный режим `release`: чистый клон использует
закреплённый GitHub Release без S3-реквизитов. Сборка, выбор версии и команды
проверяющего описаны в [инструкции Releases](docs/releases.md).
В конфигурации закреплён опубликованный [выпуск v1.0.0](https://github.com/airiga1897/OTUS_DZ07/releases/tag/v1.0.0).

Явные альтернативы разработки:

```powershell
# Сохранить реквизиты локально с ограниченными правами
. .\scripts\env.ps1 -SaveLocal

# В другой сессии явно загрузить файл в окружение
. .\scripts\env.ps1 -Development
# Сокращение: -Dev
```

Для S3 эти режимы используются с `-Artifacts`. `-SaveLocal` и `-Development`
взаимоисключающие. Python и Terraform читают только окружение.
Credentials, state, журнал этапов, контекст, ключи и секреты приложения исключены из Git.

## Развёртывание и проверка

Ansible запускается на app как отдельная systemd-операция и продолжает работу
при обрыве SSH или Wi-Fi. Повторный `deploy` из того же клона возобновляет
наблюдение за сохранённым ID; новый запуск не создаётся, пока исход операции
не подтверждён. До завершения не меняйте исходники и параметры запуска.
Состояние «связь недоступна, результат неизвестен» отличается от ошибки Ansible.
[Восстановление связи и безопасное удаление](docs/ansible-operations.md).

Первый и повторный запуск systemd-операции подтверждены в облачном прогоне.
Обрывы связи и перезапуск контроллера проверены локально с mock SSH/systemd;
намеренный обрыв реального подключения не выполнялся.

```powershell
# Развернуть; повторный вызов применяет конфигурацию к действующему стенду
.\.tools\venv\Scripts\python.exe scripts/lab.py deploy

# Проверить приложение, логи и штатное состояние кластеров
.\.tools\venv\Scripts\python.exe scripts/lab.py verify

# Проверить локальные state/context, показать размещение и URL, открыть сайт
.\.tools\venv\Scripts\python.exe scripts/lab.py open
```

После `deploy` стенд остаётся работающим. Сайт доступен по HTTP на публичном IP
app; Kibana — по тому же адресу на порту 5601, только с разрешённых /32.
Имя для Kibana — elastic, созданный пароль находится в `.local/secrets.json`
и не выводится в отчёты. SSH сохраняет порт 22. Elasticsearch и БД напрямую
из Интернета недоступны.

При нехватке хостов очищается только неуспешная попытка текущего узла;
предыдущие ВМ, сети и подключения сохраняются. Новый кандидат выбирается
после аудита удаления этой попытки.
Ошибка повторной настройки сохраняет ресурсы и данные
восстановления. Проверка Terraform-плана блокирует удаление, замену и смену
идентичности существующих ресурсов. Порядок пулов не переносит действующий стенд.
Подробности: [эксплуатация](docs/operations.md).

## Отдельное удаление

```powershell
# Удалить и подтвердить отсутствие ресурсов через state и API
.\.tools\venv\Scripts\python.exe scripts/lab.py destroy

# Дополнительно удалить файлы ДЗ07 в подтверждённом префиксе S3
# Сам бакет сохраняется
.\.tools\venv\Scripts\python.exe scripts/lab.py destroy --purge-artifacts
```

Обычное удаление сохраняет пакеты и версии исходников в S3. Реквизиты разработки
удаляются отдельно явным действием. При ошибке очистки сохраняются state,
контекст и ключи для повторного destroy.

## Временное полное испытание

**Команда уничтожает созданный ею тестовый стенд**, включая данные и media.
Она разрешена только при отсутствии действующего стенда, непустого state
и незавершённых операций.

```powershell
.\.tools\venv\Scripts\python.exe scripts/lab.py test-cycle
```

Сценарий создаёт исходный стенд, записывает контрольные данные и media,
повторяет deploy, проверяет документы Elasticsearch и ID
существующих ресурсов без добавления и выключения узлов.
В finally удаляются только ресурсы собственного запуска;
удаление проверяется через state и API. Ошибка удаления сохраняет данные
восстановления и неуспешный результат.

## Дополнительные эксплуатационные сценарии

Дополнительные эксплуатационные сценарии выполняются только явно:

```powershell
# Временно выключить master ES, проверить смену master и восстановить ВМ
.\.tools\venv\Scripts\python.exe scripts/lab.py verify --es-failover

# Подключить data/ingest-узел es4 к существующему стенду
.\.tools\venv\Scripts\python.exe scripts/lab.py add-es4
```

Это отдельные возможности развития проекта, основанные на повторно используемых
механизмах серии ДЗ. Обычные verify и test-cycle их не вызывают.
[Порядок, восстановление и ограничения](docs/optional-elasticsearch.md).
Новые сценарии проверены только локально; облачный прогон не выполнялся.

## Подтверждение и ограничения

[Полный test-cycle в ru-2a](docs/ru2-test-cycle-summary.json) подтвердил:
четыре ВМ, три физических хоста Elasticsearch, состояние кластера `green`,
работу сайта и SQL, сохранность данных и media, повторный deploy без смены
ID ресурсов и сохранность документов Elasticsearch.
[Журналы всех служб](docs/logs-verification.json) поступают в кластер:
Nginx, Django/uWSGI, HAProxy, PostgreSQL, Kibana, Elasticsearch и system.
API Kibana подтвердил доступность, представление `otus-logs` и дешборд.
[Удаление стенда подтверждено state и API](docs/cleanup-result.json).

[Доставка опубликованного выпуска](docs/release-public-verification.json) проверена
из чистого клона: подготовка окружения и получение закреплённого манифеста без S3.
[Облачный прогон через GitHub Releases](docs/release-cloud-acceptance.json) подтвердил
обычный deploy/verify, полный test-cycle, повторный deploy и удаление обоих стендов.
ВМ получили исходники и пакеты по HTTPS с проверкой SHA512.
[Локальные результаты](docs/local-verification.json): 750 тестов, 100% строк
и 98,2143% ветвей без дополнительных исключений рабочего кода.

Elasticsearch настроен с тремя master-eligible узлами и репликой индексов.
Принудительные отказы ВМ в обычном verify и test-cycle не выполняются.
Общая ВМ app — единая точка отказа сайта, БД и Kibana. HTTP не шифрует
сессию браузера; доступ к Kibana ограничен IP. Позиции чтения Filebeat и дисковая
очередь не гарантируют отсутствие потерь при любой аварии.
